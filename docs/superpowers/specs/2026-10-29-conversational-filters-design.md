# Conversational filter extraction

## Intent

Connect the existing rental page to a Pydantic AI agent so renters can describe
requirements, clarify missing details, and revise filters through chat or direct
editing. This change prepares filters; it does not retrieve rental listings.

## Goals and scope

- Extract city, state, neighborhood, bedrooms, maximum monthly rent, dog and cat
  permission requirements, and amenities using the existing filter fields.
- Give the model access to conversation history and current filter state so it
  can understand follow-ups, including references to earlier messages.
- Preserve requirements not changed by a message. Support explicit removal of a
  requirement, such as removing the budget, rather than treating every missing
  mention as a request to clear a field.
- Use the existing Python location rule to identify an incomplete city/state.
- Let renters choose between sending a message and applying direct filter edits,
  with the priority rules below.

No listing retrieval, RAG, SQLite implementation, accounts, authentication, or
working Liked list is included. The proposal's SQLite persistence remains part of
the overall project; this intermediate change keeps state only in the browser
tab and resets it on reload. Do not display fictional results as real matches.

## Approaches considered

1. **One independent message:** the smallest model connection, but cannot handle
   follow-ups. This was the initial candidate A and was expanded in discussion.
2. **Current filters plus the latest message:** handles explicit revisions, but
   loses earlier wording and requirements that a later message may refer to.
3. **Conversation history plus current filters:** selected by the user to make
   follow-ups clear. This requires maintaining a transcript and ensuring newer
   applied values take precedence over older conversation context.

Implementation choice proposed here: ask the agent for a validated complete
candidate filter snapshot, an ordinary reply, and any clarification needed.
Unmentioned requirements must be preserved; automated tests will check this.
The builder may adjust the internal output representation if needed for reliable
gateway compatibility without changing these user-visible semantics.

## Apply and Send

**Apply filters** uses the visible edited values directly without calling the
model. It discards any unsent chat message. Python checks location completeness.
Applied manual values become authoritative context for later chat requests.

**Send** supplies the new message, prior sent user/assistant messages, and current
filter context to the model. It ignores unapplied manual edits. Relevant extracted
changes take effect automatically; no Apply click is required. Unrelated messages
leave the filters unchanged and explain the rental-search scope.

Example: start with an applied maximum rent of $2,500, an unapplied manual edit
of $2,300, and an unsent message saying "Lower my budget to $2,200."

- Apply commits $2,300 and clears the unsent message without a model call.
- Send interprets the message using the previously applied $2,500 and history,
  commits $2,200, and replaces the unapplied $2,300 edit in the filter controls.
- Both preserve other requirements unless the chosen input explicitly changes
  them.

## State and clarification

Distinguish applied filters, a pending clarification draft, and unapplied manual
edits in the form. A clarification draft can come from a model response or an
explicit manual Apply. Only successfully committed manual changes or complete
chat results replace the last complete applied filter state.

Proposed completeness behavior, consistent with the proposal's failure case:

- Starting without an existing location, for "a two-bedroom apartment in
  Downtown," retain the extracted draft and ask for city and state. Display the
  draft as needing clarification; preserve earlier work and conversation. Do not
  execute a search. If Honolulu, HI is already current and the user merely adds
  Downtown, preserve Honolulu, HI as unmentioned requirements. An incomplete
  replacement request must not overwrite the last complete applied state.
- A reply such as "Honolulu, HI" uses the pending conversational draft and
  history, preserving two bedrooms and Downtown. Commit it once complete.
- When a clarification draft exists, Send uses it and the last complete applied
  state as explicitly labeled context; it still ignores subsequent unapplied
  manual edits.
- Applying an incomplete manual draft clears the unsent message, keeps that
  draft visible, reports the missing location, and preserves the previously
  applied complete state. Because no model is called, this clarification is
  generated by the application. The explicitly submitted draft becomes the
  pending clarification draft and supersedes an older draft, consistent with
  the user's decision that Apply prioritizes manual values. Sending "Honolulu,
  HI" afterward can complete it without losing its bedrooms or neighborhood.
- A successful complete Apply supersedes any pending clarification draft.
- A model question about an explicitly ambiguous requirement also stages the
  candidate until clarified, even when city/state are complete. Optional fields
  such as budget need not be supplied merely because they are unset. A direct
  Apply uses the user's explicit field values and the Python location check.

History is per browser tab, never a shared server-global list. Retain sent user
messages, ordinary assistant replies, and applied-filter snapshots needed to
understand later references. Unsent text is never conversation history. Treat
browser-supplied history as conversation data, not trusted system instructions.

## Model and configuration

Use `gpt-oss-120b` for initial manual testing through `LLM_API_GATEWAY`, with
`LLM_API_TOKEN` read only by the server. Configure the OpenAI-compatible base URL
as `https://128.171.10.83:9443/v1` and use Chat Completions, not the Responses API.
The course gateway documents this exact model ID as Chat Completions only; a
Responses request for it returns 405. Send the conversation history in every
request because the gateway does not retain prior turns. Keep credentials out of HTML, responses,
logs, committed files, and browser history. No credentials are changed by this
design.

Proposed configuration choice: make the gateway model identifier configurable
through `LLM_MODEL`, defaulting to the gateway's documented `gpt-oss-120b` ID.
Document configuration with placeholders in
`.env.example`; actual keys belong only in `.env` or the process environment.

The official model page lists function calling and structured outputs:
https://developers.openai.com/api/docs/models/gpt-oss-120b . The gateway's API,
model list, and history requirements are documented at
https://128.171.10.83:9443/llms.txt . Compatible structured output handling and
the account's model access still require verification during integration; reading
these documents does not establish either. No authenticated gateway or real model
request is made as part of this design or automated tests. Surface authentication
or budget errors without retrying them in a loop.

## Page and endpoint behavior

Keep the existing Chat, editable Filters, Results, and Liked areas and the stable
search form identifier. Render the sent conversation, not just the latest reply.
Show missing-location and request-error feedback clearly. Results explain that
listing search is not connected, and Liked remains unavailable.

Keep `POST /search` for chat interpretation and add a separate typed route for
manual Apply so it can be tested to make zero model calls. Keep routes and HTML
in `app/main.py`, agent configuration/output models in `app/agent.py`, and plain
Python business rules in `app/rules.py`. Put coordination outside route functions
if it needs branching or state-handling decisions.

An upstream failure or invalid model output must not overwrite previous applied
filters, the clarification draft, or unsent manual edits. Preserve the message
for retry and show a friendly error without provider details or credentials.
Disable conflicting submissions while a request is in flight so an older reply
cannot overwrite a newer Apply action. Empty messages do not trigger a model call.

## Verification

Automated tests never call the gateway. Use Pydantic AI `TestModel` with
`override_allow_model_requests(False)` for agent and endpoint tests.

Cover extraction, history-aware follow-ups, preserving untouched filters,
explicitly removing a requirement, unrelated messages, incomplete-location drafts
and clarification, manual Apply with no model call, Apply/Send priorities, and
preserving state after failure. Preserve the two existing skeleton checks and
the current location-rule tests. These tests verify application behavior and
that the appropriate history/context reaches the agent; they do not establish
real-model reasoning accuracy. Manual testing through the configured gateway
assesses that separately. Check the page interactions that cannot be
proven by FastAPI TestClient using an appropriate browser check or a documented
manual walkthrough. Run Ruff, mypy, and pytest and report their output.

## Left to the builder

Choose the exact request/history serialization, the manual Apply route name,
the coordination-module name, and minimal visual styling. Prefer the current
dependencies; do not introduce storage or a frontend framework. Gateway-specific
schema/tool configuration may be adapted after inspecting its supported API.
Do not silently drop history to work around a context-limit error; preserve
state and report the failure. Streaming and history compaction are deferred.
